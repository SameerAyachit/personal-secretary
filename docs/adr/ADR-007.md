# ADR-007: Repeating events are a rolling window of ordinary events

Date / Status: 2026-11-15 / accepted

Context: "Focus on the course every day, 4pm to 6pm" could not be expressed: `event_create` had no recurrence, so the model retried a one-off event until the step limit. Reminders already support `recurrence_text` (plan 9.3); events did not. Google Calendar supports RRULE masters, but pulling with `singleEvents=true` (what sync does) returns instances as separate events, so a master plus local expansion would show duplicates and every view (Today, Calendar, plan_day, conflict checks) would need expansion logic.

Decision: `event_create` takes `recurrence_text` (same grammar as reminders). Code materialises the series as ordinary `events` rows sharing a `series_id` (migration 011), for a rolling 30-day window (at most 60 rows). Each row is pushed to Google through the existing idempotent insert path. A scheduler step (`scheduler/series_job.py`) tops the window up every tick, continuing after the latest row ever created, so a deleted occurrence is never regenerated and a series whose rows are all deleted stops. The time of day always comes from `when_text`; the first occurrence is the next one after now (today if still ahead). Undo soft-deletes the series' occurrences that have not reached Google yet (`soft_delete_series`), and says so when some already did.

Consequences: Calendar, Today, plan_day and conflict checks work unchanged. The series is not one RRULE object in Google (30 separate events), so "delete the series" there is manual; `event_update` and delete affect one occurrence. Repeating all-day events and series-wide edit/cancel tools are not built. To revisit: add an `event_cancel_series` tool and switch the Google push to one RRULE master once sync can map instances back to their series.
